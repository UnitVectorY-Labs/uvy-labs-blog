**gogitup v0.6.4 was released on November 19, 2026.** This is a focused correctness release: it fixes the one situation where gogitup could mislead you about the tools it manages — when a half-finished local build of a tool was hiding the real, installed copy. If you've ever been confused by `unknown` versions in `gogitup list`, this one's for you.

For the uninitiated, gogitup is a small command-line tool that keeps the Go utilities you installed with `go install` up to date. It tracks the binaries you care about, checks upstream for newer versions, and re-runs `go install` to bring them current. For that to be useful, gogitup first has to correctly *read* what's actually installed on your machine — and that's exactly what this release tightens up.

## What's new

The headline change in v0.6.4 is a fix to how gogitup locates and inspects the binaries it manages ([PR #131](https://github.com/UnitVectorY-Labs/gogitup/pull/131), resolving [issue #130](https://github.com/UnitVectorY-Labs/gogitup/issues/130)).

Previously, if you ran gogitup from inside a directory that happened to contain an executable with the same name as a tracked tool — say, a development build sitting in your source checkout — and that directory was reachable earlier on your `PATH` (including a bare `.` entry), gogitup would report `unknown` for the tool's module, installed version, and build-time Go version. The real, properly installed binary further along your `PATH` was simply never consulted. The result was baffling output like this:

```sh
cd ~/github/ghorgsync          # this directory also holds a local ghorgsync build
PATH=".:$PATH" gogitup list --json
# ghorgsync shows up as "unknown" — even though ~/go/bin/ghorgsync is v0.7.0
```

In v0.6.4, gogitup now searches your `PATH` in order but deliberately skips any entry that points back to your current working directory. Absolute paths, relative forms, and symlinks that alias the current directory are all handled, so the lookup lands on the genuinely installed binary and reads its real metadata. Version reporting, update detection, rebuild decisions, and add/install verification — which all share this lookup — are now consistent.

If a tracked tool exists *only* as a build in your current directory and isn't installed anywhere on your `PATH` outside it, gogitup will now say so plainly ("binary not found") rather than reporting misleading details from the local build. This is the intended, documented behavior, and it's been written up in the [usage documentation](https://unitvectory-labs.github.io/gogitup/).

The rest of v0.6.4 is behind-the-scenes maintenance that doesn't change how the CLI behaves for you: a documentation-site diagram-library refresh, a couple of routine CI security-scanner workflow bumps, and some repository template housekeeping. None of it affects your commands or configuration, and there are no breaking changes — no commands, flags, or config files changed.

## Why it matters

A tool whose whole job is telling you what's installed lives or dies by its accuracy. When gogitup reported `unknown` versions because of a stray local build, it wasn't just cosmetic: the same version-reading feeds `check`, `upgrade`, and `add`, so a shadowed binary could leave you unsure whether you were actually up to date. By making the current directory invisible to the installed-binary search, v0.6.4 removes a confusing failure mode that most often showed up precisely when you were actively developing a tool with gogitup nearby.

The practical upshot is peace of mind: what `gogitup list` and `gogitup check` report now reliably reflects the binaries you installed, regardless of what you happen to be building in the directory you're standing in.

## Upgrading

v0.6.4 requires no migration steps — pick whichever install method you already use:

- `go install github.com/UnitVectorY-Labs/gogitup@latest`
- Download the archive for your platform from the [v0.6.4 release page](https://github.com/UnitVectorY-Labs/gogitup/releases/tag/v0.6.4) (Linux/macOS `.tar.gz` and Windows `.zip`, each with `.md5` and `.sha256` checksums) and place it on your `PATH`
- If you already manage gogitup with itself (`gogitup add gogitup`), just run `gogitup upgrade`

After upgrading, re-run `gogitup check` or `gogitup list`: rows that previously showed `unknown` for tools shadowed by a local checkout should now display their real versions. One small note — gogitup intentionally ignores your current directory during lookups now, so make sure the directory holding your installed binaries is on your `PATH`.
