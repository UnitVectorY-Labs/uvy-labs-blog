cfgraft v0.4.2 was released on November 18, 2026 — just two days after v0.4.1 — and it lands two upgrades that make the tool feel markedly more complete: cfgraft can now safely update its own configuration as part of a normal sync, and every conflict it encounters now tells you exactly what went wrong and the precise command to fix it.

If you're new here: cfgraft is a small Unix-style CLI for safely syncing files and directories from Git repositories into local configuration paths. You declare Git sources and source-to-destination mappings in `~/.config/cfgraft/config.yaml`, run `cfgraft sync`, and it refreshes your dotfiles and other config from the repos you trust — while refusing to clobber anything it doesn't manage. This release deepens that core loop rather than adding surface features, which is exactly the kind of polish a tool you run against your own home directory should earn.

## What's new

### Your config can now be one of the things cfgraft manages

The headline change: a mapping may now target cfgraft's own `config.yaml`. That means your dotfiles repo can version-control cfgraft's configuration and roll it out like any other managed file — and when a sync replaces that config, cfgraft doesn't stop halfway.

When a planned write would replace its own active configuration, cfgraft validates and parses the replacement, then re-plans the *same* sync against it: newly referenced repositories are refreshed, brand-new mappings are applied, and state for removed mappings is pruned. As the updated usage docs put it, "an additional sync is not required." You'll see a `planning with updated configuration` message when this happens.

All of cfgraft's usual caution still applies. An invalid replacement config, a configuration cycle, or a chain of more than 16 config updates fails the sync *before anything is written*, and cfgraft refuses to delete the config it is actively running from. The normal safety model is untouched: an unmanaged config that differs from the source still requires `sync --force`, and `sync --dry-run --force` lets you preview the whole replacement before committing to it. Removing a self-management mapping installs the accepted config and simply stops tracking it.

This capability is opt-in — it only activates if you add a mapping that points at cfgraft's own config file.

### Conflicts now come with instructions

Nobody likes a mystery conflict. In v0.4.2, conflict reporting was rewritten around one idea: every conflict should name the problem and hand you the fix.

- The vague "existing destination has no state entry" reason is gone, replaced with a plain-language explanation: the destination is not managed by cfgraft yet and differs from the source.
- Every conflict line in `sync` and dry-run output now embeds the exact remediation command — whether you want to overwrite with source content, delete the destination, or take an existing file under management.
- Dry runs end with a `next:` line suggesting the command to preview or apply the plan, and a forced plan now clearly labels its pending overwrites instead of looking identical to a blocked one.
- `cfgraft diff` now always shows conflicts — with the resolving command — before the actual diff, no `--verbose` flag required.
- Even simple mistakes are friendlier: typing `cfgraft --dry-run` now tells you the flag belongs on the subcommand and suggests `cfgraft sync --dry-run`.

## Why it matters

Self-managed configuration sounds like a niche trick, but it closes a real gap in the "everything from one repo" workflow. Before this release, updating cfgraft's own config from your dotfiles repo meant editing it by hand or running an awkward extra sync to pick up the new state. Now the config that defines what cfgraft does is itself just another version-controlled, hash-tracked, conflict-protected file — and a single `cfgraft sync` can simultaneously update your shell config, your editor config, *and* the rules governing how cfgraft syncs them. The pre-write validation, cycle detection, and chain limits matter here precisely because the tool is rewriting the rules it runs on: a bad config can't leave you halfway between two states.

The conflict-message rework is smaller but touches every user. Conflict protection is cfgraft's central safety promise, and a safety net is only as good as your ability to act on it. Turning each conflict into a copy-pasteable next step removes the guesswork from the one situation where a wrong `--force` is costly — and it makes dry runs genuinely actionable rather than just informational.

## Upgrading

There's nothing special to do. v0.4.2 is a drop-in upgrade with no configuration-format changes and no migration steps: grab the archive for your platform (Linux, macOS, or Windows; 386/amd64/arm64) from the GitHub Releases page for v0.4.2 — checksums are included — or rebuild the single Go binary from source. If you're on v0.4.1 from two days ago, the same install path applies.

One thing to keep in mind if you script around cfgraft: conflict and diff output wording changed (the old "existing destination has no state entry" string, for example, is gone, and `diff` now prints conflict notes without `--verbose`). Commands and exit behavior are unchanged, but anything parsing cfgraft's exact output strings may need a tweak.

If you've ever wanted your entire configuration — including the sync tool's own rules — to arrive from a `git push`, this is the release that makes that a one-command operation.
