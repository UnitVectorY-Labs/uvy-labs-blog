cfgraft v0.4.1 was released on November 16, 2026, and it tackles one of the oldest frustrations of managing dotfiles across several machines: the shared config that knows too much. If you keep a single `config.yaml` synced from a Git repo to a laptop, a desktop, and a server, you've probably felt the pinch — machine-specific entries that have to be commented out, duplicated config variants, or carefully arranged repo folders just so each machine picks up the right pieces.

This release adds *machine-local conditions*, a simple opt-in mechanism that lets each machine decide which sources and mappings actually apply to it — no edits to the shared config required.

## What's new

Sources and mappings in `~/.config/cfgraft/config.yaml` can now carry an optional `condition` field:

```yaml
sources:
  dotfiles:
    repo: https://example.com/dotfiles.git
    ref:
      type: branch
      name: main
    mappings:
      - source: mac/app.conf
        target: ~/.config/app.conf
        condition: mac
      - source: linux/app.conf
        target: ~/.config/app.conf
        condition: linux
```

An entry with `condition: NAME` is active only on machines where a small marker file — `~/.config/cfgraft/condition-NAME` — exists. On your Mac you run `touch ~/.config/cfgraft/condition-mac`; on your Linux box, `touch ~/.config/cfgraft/condition-linux`. Each machine then syncs only the entries it opted into — so two mappings can even share the same destination path, since the machine carrying only its own marker will activate just one of them.

A few details worth knowing:

- **Sources can be conditioned too.** A condition on a whole source disables everything it contains — including the repository refresh — so a machine never even clones or fetches a repo it won't use.
- **Conditions stack sensibly.** If both a source and one of its mappings have conditions, both must be enabled for the mapping to run; a plain mapping follows its source.
- **You can see the status.** `cfgraft validate` still checks your entire config, and now reports each condition as enabled or disabled, so you can confirm what will and won't sync before you run anything.
- **Marker contents don't matter.** Presence is the signal; just create a regular file with the right name (letters, digits, underscores, and hyphens, starting with a letter or digit).

## Why it matters

For anyone who maintains one cfgraft config across multiple machines, this turns a compromise into a feature. Instead of carving out per-machine config variants or commenting entries in and out, you can commit everything — every machine's mappings, every machine's sources — and let local marker files do the selecting. The shared config becomes a complete description of your setup, and each machine reads the parts that concern it.

It also builds directly on v0.4.0's portable home paths (the `~/.config/cfgraft/home` override, landed just a day earlier). Together, the two mechanisms give you a consistent story: your `config.yaml` stays shared and portable, while per-machine differences live in small, out-of-band marker files next to it.

Existing setups are untouched. Entries without a `condition` behave exactly as before, the config format breaks nothing, and there are no new commands or flags — conditions are strictly opt-in, per entry.

One behavior to keep in mind: toggling a marker off is treated like removing the entry from your config. The next `sync` will clean up the entry's tracking state but will *not* delete the files it previously placed, and if you re-enable the condition later, cfgraft's usual conflict protection applies if the destination changed in the meantime. Think of markers as a switch for *participation in sync*, not a delete/restore toggle.

## Getting cfgraft v0.4.1

Upgrading is as simple as swapping in the new binary — your existing config works as-is. Prebuilt binaries for v0.4.1 are available on the [GitHub release page](https://github.com/UnitVectorY-Labs/cfgraft/releases/tag/v0.4.1) for macOS (amd64/arm64), Linux (386/amd64/arm64), and Windows (386/amd64), each accompanied by MD5 and SHA256 checksums. If you have a Go toolchain, `go install github.com/UnitVectorY-Labs/cfgraft@latest` will grab the newest release, or you can build from source with a `git clone` and `go build`.

Once you're on v0.4.1, give the feature a try: tag one machine-specific mapping with a `condition`, `touch` the matching marker file on the machine where it belongs, and run `cfgraft validate` to watch the status flip to enabled. It's a small knob, but for a fleet of machines sharing one config, it's the one that finally lets the config stop making everyone agree.
